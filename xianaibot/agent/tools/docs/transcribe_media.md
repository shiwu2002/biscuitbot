# transcribe_media

把一个**本地**音频或视频文件里的说话内容转写（transcribe / ASR / 语音识别）成文字，
返回完整文字稿。底层走 OpenAI Whisper 兼容的 `audio/transcriptions` 接口
（whisper-1 等模型），不依赖任何本地解码库。

它只处理**声音**：视频画面既不抽帧也不上传，10 分钟视频与 10 分钟纯音频的开销
一样（≈ 2k token 的文字稿）。这与「把视频逐帧送给模型看」相差 2–3 个数量级，
是本工具存在的前提。

## 何时使用

- 用户发来一段录音 / 语音 / 视频，并问「说了什么」「帮我整理成文字」「总结一下会议」。
- 你需要音频里的信息才能回答，而消息正文里**没有**现成的转写文本。

**不要**在这些情况下调用：

- 正文里已经有转写文本（渠道语音消息常常内联了 `[transcription: …]`，见下方「重复转写」）。
- 用户只是想让你确认收到了文件、或只是问文件大小/时长。
- 你要的是画面内容——本工具拿不到画面。画面相关需求走 `video-understanding`
  技能（抽 6–12 帧再逐张 `read_file`）；没有 ffmpeg 就如实告诉用户看不到画面。

## 参数

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| path | string | 是 | - | 本地音视频文件路径。用户附件在消息里以 `[用户附加音频：<路径>]` / `[用户附加视频：<路径>]` 给出，该路径可直接用 |
| language | string | 否 | 配置默认 | 音频语言的 ISO-639-1 小写代码（`zh` / `en` / `ja` / `yue` 等）。给了能明显减少同音字错字；不确定语言就不要猜，留空让服务端自动识别 |

不支持 http(s) 直链，也不支持 provider / model 覆盖（转写服务商由配置
`transcription.provider` 决定，见「未配置或报错时怎么办」）。

## 调用示例

```
# 用户发来一段会议录音并问「讲了什么」
transcribe_media(path="media/2026-09-25/meeting.m4a")

# 明确知道是中文访谈，指定语言以降低错字
transcribe_media(path="media/2026-09-25/interview.mp3", language="zh")

# 用户发来视频问「里面那人说了什么」（只转写音轨，不看画面）
transcribe_media(path="media/2026-09-25/demo.mp4")
```

返回值是 JSON：`transcription.text` 为完整文字稿，另有 `provider` / `model` /
`language` / `chars` / `bytes` 便于说明与排查。文字稿较长时框架会自动落盘并给出
预览，不需要你手动截断。

## 成本与上限（必读）

- **计费口径按音频秒数**（不是你我的 token），所以调用前先想清楚「用户要的是不是
  文字内容」。一次 10 分钟录音的文字稿约 2k token 进上下文，成本远低于逐帧看视频。
- **体积是唯一护栏**，且三道都不宽：WebUI 单文件 20MB、单条消息 24MB、转写服务 25MB。
  超限时**文件根本传不进来**（不是「转写慢」），本工具会直接返回体积错误。
- 换算参考：mp3 128kbps ≈ 0.96MB/分钟 → 20MB ≈ 21 分钟；低码率录屏（~300kbps）
  ≈ 9 分钟；≤2 分钟的 720p 小视频可用。
- **10 分钟 720p 视频约 110–190MB，是上限的 5–9 倍**，手机拍的 5 分钟以上 1080p、
  会议录屏同理——这类文件不能直接转写，要先**只抽音轨**（本地 ffmpeg，
  10 分钟 → 约 2–3MB），再用本工具转写那条音轨：

  ```
  ffmpeg -y -i "clip.mp4" -vn -ac 1 -ar 16000 -c:a aac -b:a 32k clip_audio.m4a
  ```

  本工具**不代做这一步**（它不调用 ffmpeg）。完整的成本阶梯（何时该转写、何时
  该抽帧、没有 ffmpeg 时怎么说）见 `video-understanding` 技能。本工具不承诺
  「按文件时长拒绝」，只说体积。
- 同一文件同一问题**只调用一次**。服务端对同一段音频不会给出不同结果，重复调用
  只会在计费上翻倍。

## 未配置或报错时怎么办

工具**永不从工具表里消失**，因此错误信息本身就是排查指引。几种典型返回：

| 返回片段 | 含义 | 怎么办 |
|---|---|---|
| `语音转写未配置 API Key（当前生效的 provider 是 'groq'）` | 默认 provider 是历史遗留的 `groq`，它只读 `providers.groq.apiKey`、不读环境变量 | 要么在「模型厂商」页给该厂商填 Key，要么在「设置 → 语音转写」把 provider 换成已配置 Key 的厂商。**把原因如实转达用户** |
| `语音转写功能已被关闭（transcription.enabled=false）` | 用户显式关闭了该能力 | 请用户在「设置 → 语音转写」打开；模型无法自行开启 |
| `不支持 http(s) 直链` | 传了 URL | 先用 shell 工具把文件下载进工作区，再传本地路径 |
| `文件过大：… 超过转写上限 25MB` | 超过 `transcription.max_upload_mb` | 按 `video-understanding` 技能的「只抽音轨」一步压成低码率音轨后再转写；本机没有 ffmpeg 就如实告诉用户 |
| `路径越界` | 目标在工作区与媒体目录之外 | 改用工作区内的路径（工作区边界是硬性安全策略，不可绕过） |
| `不支持的文件类型` | 不是音频/视频 | 文档类内容用 `read_file` / `extract_documents` |
| `转写返回空文本（provider=… model=…）` | 服务端拒绝（4xx）、超时，或音频里没有人声 | 日志里有状态码与响应体（搜 `transcription HTTP`）。**不要换工具重试**，把失败原因与文件名、体积告诉用户 |

失败原因在服务层会被折叠成空串（历史设计），所以日志里的 `transcribe_media:` 与
`transcription HTTP` 两行是唯一的一手证据，排查时先看它们。

## 为什么这个工具总是注册

上下文层的附件说明会点名 `transcribe_media`（`[用户附加音频：…（…用 transcribe_media
转写…）]`）。如果因为「没配 Key」或「能力被关闭」就把它从工具表里摘掉，模型看到的是
`Tool 'transcribe_media' not found`——它改不了配置，于是只能反复重试或对用户敷衍。
所以本工具的 `enabled` 恒为 `True`，由 `execute` 返回上面那张表里的可操作错误：
**用户因此知道「这个能力存在、该怎么打开」**。

注意「不门控」不等于「不看配置」：`transcription.enabled=false` 会在 `execute`
第一步被拦下，返回明确的「已被关闭」。

## 已知边界

- 只支持本地文件与工作区/媒体目录内的路径，不接受 URL（服务端不代下载）。
- 只按体积判断，不按时长：仓库里没有任何解码/探测库，无法在本地读音频时长。
- `.flac` / `.opus` 不在 WebUI 拖拽白名单里（拖不进），但渠道消息与 API 附件可以，
  本工具也接受。
- 不做说话人分离、不返回时间戳、不做翻译——返回的是单一纯文本稿件。
- 转写结果不落盘缓存：同样的文件再调一次会再花一次钱。
