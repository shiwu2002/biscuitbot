# 图像 / 视频生成手法

> 本技能提供的是「怎么做得对」的**方法**：判断意图、扩写提示词、控制变体、诚实交付。
> 它**不提供生成引擎**，也**不假定任何模型**——具体用哪个工具、哪个模型，
> 由下面的「生成能力从哪来」现场决定。
>
> **提示词是你自己的职责。** 与一些把提示词交给私有后端代写的外部服务相反：
> 本项目要求**你**先把用户的原始需求扩写成专业提示词再调用工具
> （见 `docs/generate_image.md`：「调用前必须先优化提示词」）。

## 生成能力从哪来（先看这一节）

**本技能只提供「怎么做得对」的方法，不提供生成引擎。** 真正的生成能力必须现场发现，
不同用户、不同时间的可用情况可能完全不同。按下面顺序判断，**不要假设任何模型名**。

1. **先发现，再动手。** 用 `discover_tools("生成图片")` / `discover_tools("生成视频")`
   确认当前到底有哪些生成工具可用。本项目的原生工具是 `generate_image`（图片）与
   `generate_video`（视频），调用前用 `read_file` 读它们的使用说明
   （`docs/generate_image.md` / `docs/generate_video.md`），按真实参数传参。
2. **优先用原生工具。** 用户在本机配置里已经决定启用哪些厂商与模型，那是他的选择，
   不要替他改、也不要在提示词里写死某个模型名。需要的是「具备某种能力的模型」——
   例如「文字渲染准确的模型」「角色一致性强的模型」「支持参考图的编辑模型」——
   然后从实际可用的工具与模型里挑最合适的一个，并在回复里说明你挑了哪个、为什么。
   工具的 `model` / `provider` 参数留空即走用户配置的默认值，**除非用户明确指定**。
3. **用户配了 MCP 生成服务就优先用它。** 如果 `discover_tools` 或
   `cold_storage` 找到 `mcp_` 前缀的生成类工具（用户在 `tools.mcpServers` 里
   自己接的服务），说明用户有意为此付费/自建，应当优先使用；同样先读它的说明再调用。
4. **一个都没有时，诚实说明，不要硬编。** 如果确实找不到任何可用的生成工具：
   - 明确告诉用户「当前没有可用的图像/视频生成能力」，并指出这是开关问题不是能力问题
     （图片生成开关：`tools.imageGeneration.enabled`；视频生成开关：
     `tools.seedanceVideo.enabled`，可在「模型厂商」页配置密钥）。
   - **绝对不要**改用 `exec` 去调某个第三方 CLI、去装某个未配置的服务、或凭空编造一个
     看起来像结果的图片路径。也不要假装生成成功。
   - 可以退而求其次：如果你能用 `exec` + 本地库（如 ffmpeg、Pillow）做出**确定能做出**的
     替代产物（例如纯色占位图、文字海报），先说明这是替代方案，再做。
   - 把选择权交回用户，问他是要打开开关、配置厂商，还是换一个不需要生成的做法。

## 第一步：先判断用户到底要哪一种

图片与视频都能生成时，**别猜错产物类型**：

- 「把这张图动起来」「让它动/走/说话」→ 视频，不是图片。
- 「改一下这张图」「换个背景」「去掉那个人」→ 编辑已有图片（走 `reference_images`），不是从零生成。
- 「画一张…」→ 从零生成图片。
- 一次要「一套图」、多张不同版本 → 见下面的「多图与变体」。

## 第二步：按能力路由，别按模型名路由

不要背模型清单。**先问「这件事需要模型具备什么能力」，再从实际可用的工具与模型里挑。**
下表把常见意图翻译成能力需求与提示词对策：

| 用户意图 | 需要的能力 | 怎么落到提示词 |
|---|---|---|
| 角色/人物反复出现，要保持同一张脸 | 角色一致性强的模型；优先传参考图锚定 | 把角色的稳定描述写成**固定段落**，每次原样复用；换姿势/场景时只改动作与环境，不改外貌描述 |
| 电影感单帧、海报感 | 擅长构图与光线的模型 | 用镜头语言写（焦段、机位、光比、景深），见 `references/prompt-engineering.md` |
| Logo / 画面里要有具体文字 | **文字渲染准确**的模型 | 把要出现的文字**逐字加引号**写进提示词，并说明字体气质与位置；生成后必须核对有没有错字 |
| 改已有照片（换风格 / 换背景 / 去物） | 支持参考图编辑的模型 | 传 `reference_images=[该图本地路径]`，提示词**只描述要改什么**，不重新描述原图 |
| 产品 / 营销物料 | 见 `product-photoshoot`、`marketplace-cards` 技能 | 不在本技能里硬做，交给那两个技能 |
| 视频 / 让照片动起来 | 视频生成能力 | 提示词写**运动**，不要重复描述静态画面；见参考文件的视频段落 |

挑好之后，**在回复里用一句话说明你选了哪种能力/工具以及为什么**（用户配了什么模型不用报，那是他自己的配置）。

## 第三步：生成前必须扩写提示词

**这是硬性要求，不是建议。** 用户说「画只猫」，你不能把「一只猫」原样传给工具。
把原始需求扩写成包含以下维度的详细描述：

**主体 + 环境 + 风格/媒介 + 构图/镜头 + 光线/色彩 + 氛围**

```
# 弱（不要这样）
"一只猫"

# 强
"一只毛茸茸的橘猫蜷在雪松林间的木屋窗台上，冬日黄昏的金色逆光，
 窗玻璃结霜，暖色室内灯与冷色雪景形成色温对比，85mm 中焦浅景深，
 胶片颗粒质感，安静治愈的氛围"
```

视频的提示词按 **主体 → 动作 → 环境 → 运镜 → 风格** 组织，写法细节与更多对照示例
见 `references/prompt-engineering.md`。

**按需加载**：动笔写提示词前，先 `read_file` 读本技能目录下的
`references/prompt-engineering.md`。里面是图生图、图生视频、否定式表述、画幅、文字渲染、
安全边界等具体手法，比本文正文更细。设计品类（海报/Logo/封面/电商主图/社媒配图）另见
`references/design-methodology.md` 的需求确认清单、设计原则与品类自查流程。

## 第四步：多图与变体

- `generate_image` 的 `count` 支持 1–8（还受配置的每轮上限约束）。
- **`count` 加大时，让每张在预设、光线、角度、配色上真正不同**——不要用同一句提示词
  换几个形容词充数。生成后自己先看一眼，同质化就重写提示词重来。
- 要「一套风格统一的图」时，先定一张为基准，后续用 `reference_images=[基准图路径]`
  锚定，保证风格与主体一致。

## 第五步：多片段视频

要生成较长视频时，不要指望一次调用搞定：

1. 先做故事/分镜规划，把长视频拆成若干约 10 秒的独立片段，按顺序编号。
2. 每个片段单独调 `generate_video`，通过共享关键视觉元素（角色、服装、背景、色调）衔接。
3. **让片段首尾连贯**：把上一段的尾帧作为下一段 `image_urls` 的**首个元素**
   （`image_urls` 的第一个元素会被当作首帧参考）。
4. 全部片段生成后，用 FFmpeg concat 合并（`-c copy` 直接复制流，避免重编码丢音频）。

更多时长/分辨率/厂商参数差异（例如某些厂商只支持部分画幅值，越界值会被静默丢弃）
以 `docs/generate_video.md` 为准——**先读文档再传参**。

## 第六步：交付

- 生成结果会持久化为本地产物，工具返回**本地路径**。
- **用 `message` 工具的 `media` 参数把文件发给用户**，让用户在聊天里直接看到图/视频。
- **不要把本地路径、工具调用文本、内部标记贴给用户**——那些对他没用，还会污染上下文。
- 回复保持简短：交付了什么东西、几张/几秒、你为它选了哪种生成能力。不要回贴完整提示词，
  除非用户明确要。

## 常见错误

| 错误 | 后果 |
|---|---|
| 直接把用户的短句当提示词传下去 | 出图平庸、细节缺失 |
| 提示词里写死某个模型名 | 用户没配该模型时直接失败；也越权替他做了配置决定 |
| 改了图却重新描述整张原图 | 模型会重画原图，原来的内容被改掉 |
| 视频提示词里描述静态画面 | 浪费提示词预算，运动反而不明确 |
| `count` 调大但变体只是换个形容词 | 出来一堆几乎一样的图 |
| 把本地路径 / 提示词全文贴给用户 | 用户看不懂，上下文被污染 |
| 找不到生成工具就编一个结果路径 | **最严重**——欺骗用户。必须如实说明并交回选择权 |
