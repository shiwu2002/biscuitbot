# 电商上架图卡

> 本技能管的是**要上架卖的合规交付物**：主图、副图、A+ 模块，以及它们的一致性。
> 关心的是「**这套图能不能过平台、能不能卖货**」，不是纯粹的视觉好看。

**与 `product-photoshoot` 的分工**：那边做**品牌级营销图**（广告、种草、社媒、横幅），
这边做**要上架的合规交付物**。用户说「上架 / 主图 / 详情页 / A+ / 商品卡片」时是这边；
只是要「好看的产品图 / 广告图」时去那边。两边都要时，先用那边定视觉基调，再用这边出全套。

## 生成能力从哪来（先看这一节）

**本技能只提供「怎么做得对」的方法，不提供生成引擎。** 真正的生成能力必须现场发现，
不同用户、不同时间的可用情况可能完全不同。按下面顺序判断，**不要假设任何模型名**。

1. **先发现，再动手。** 用 `discover_tools("生成图片")` / `discover_tools("生成视频")`
   确认当前到底有哪些生成工具可用。本项目的原生工具是 `generate_image`（图片）与
   `generate_video`（视频），调用前用 `read_file` 读它们的使用说明
   （`docs/generate_image.md` / `docs/generate_video.md`），按真实参数传参。
2. **优先用原生工具。** 用户在本机配置里已经决定启用哪些厂商与模型，那是他的选择，
   不要替他改、也不要在提示词里写死某个模型名。需要的是「具备某种能力的模型」——
   例如「文字渲染准确的模型」「角色一致性强的模型」「支持参考图的编辑模型」——
   然后从实际可用的工具与模型里挑最合适的一个，并在回复里说明你挑了哪个、为什么。
   工具的 `model` / `provider` 参数留空即走用户配置的默认值，**除非用户明确指定**。
3. **用户配了 MCP 生成服务就优先用它。** 如果 `discover_tools` 或
   `cold_storage` 找到 `mcp_` 前缀的生成类工具（用户在 `tools.mcpServers` 里
   自己接的服务），说明用户有意为此付费/自建，应当优先使用；同样先读它的说明再调用。
4. **一个都没有时，诚实说明，不要硬编。** 如果确实找不到任何可用的生成工具：
   - 明确告诉用户「当前没有可用的图像/视频生成能力」，并指出这是开关问题不是能力问题
     （图片生成开关：`tools.imageGeneration.enabled`；视频生成开关：
     `tools.seedanceVideo.enabled`，可在「模型厂商」页配置密钥）。
   - **绝对不要**改用 `exec` 去调某个第三方 CLI、去装某个未配置的服务、或凭空编造一个
     看起来像结果的图片路径。也不要假装生成成功。
   - 可以退而求其次：如果你能用 `exec` + 本地库（如 ffmpeg、Pillow）做出**确定能做出**的
     替代产物（例如纯色占位图、文字海报），先说明这是替代方案，再做。
   - 把选择权交回用户，问他是要打开开关、配置厂商，还是换一个不需要生成的做法。

> 本技能的交付物清单**不绑定模型**——清单决定的是「要交哪几张、每张解决什么」，
> 具体由哪家模型渲染由上面第 2 条现场决定。

## 第一步：先读清单，再动手

用户提到上架、主图、副图、详情页、A+、商品卡片，或说「出一套电商图」时，
**先 `read_file` 读本技能目录下的 `references/marketplace-checklist.md`**，
按里面的交付物清单逐项和用户确认范围，**确认完再开始生成**。

清单里包含：

- **4 个常用范围**：只做主图 / 主图+5 张副图 / 主图+7 个 A+ 模块 / 全套
- **13 个交付物名称**及其各自要解决的问题（`main_image`、`infographic`、`multi_angle`、
  `detail_shot`、`lifestyle`、`whats_in_box`、以及 7 个 `aplus_*` 模块）
- **主图合规要点**（白底、主体占比、禁促销文字等）与「平台规则会变」的免责边界
- **同链接一致性纪律**

别凭记忆生成——清单里的项目是「有没有交付到位」的核对标准。

## 第二步：先出主图，再出其余

顺序很重要：

1. **先做主图**（`main_image`），和用户确认产品外观、配色、光线语言都对了。
2. **把这张主图作为后续所有图的 `reference_images`** 传入，锚定产品外观与视觉系统。
   这是同一链接下所有图「看起来是一套」的唯一可靠手段。
3. 再按确认的范围依次出副图与 A+ 模块。

## 第三步：合规自检

生成后**逐项核对** `references/marketplace-checklist.md` 里的合规要点，特别是：

- 主图背景是否够干净、有无多余文字/水印/边框
- 产品外观在整套图里是否**完全一致**（同一个包装、同一个颜色、同一个 logo）
- 画面里的文字（品名、卖点、参数）是否**逐字正确**——文字渲染出错就换一个擅长
  文字渲染的模型重做那张，不要硬交付

**平台规则会变**：具体尺寸、白底要求、允许的文字比例等，以用户实际要上架的平台为准。
不确定时**问用户或让用户查平台规则**，不要编造一个数字糊弄过去。

## 交付

- **用 `message` 工具的 `media` 参数把图发给用户**，按交付物名称分组列出。
- 回复保持简短：交付了哪几张、分别是什么用途、还差哪几张没做。
- **不要把提示词全文、本地路径、内部模式名贴给用户**。
- 有图生成失败就如实说明，不要用其他图冒充。

## 反面清单

| 错误 | 后果 |
|---|---|
| 不读清单直接开做 | 漏交付物，用户上架时才发现缺图 |
| 每张图各自独立生成、不传主图做参考 | 整组图产品外观不一致，看起来不像同一件商品 |
| 主图背景花哨 / 有促销文字 | 可能过不了平台审核，白做 |
| 画面文字错了还交付 | 用户上架后被投诉或下架 |
| 编造平台的具体尺寸/合规数字 | 用户按错的信息做，损失更大 |
| 找不到生成工具就编一个结果路径 | **最严重**——欺骗用户。必须如实说明 |
