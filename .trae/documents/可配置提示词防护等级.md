# 可配置提示词防护等级（guard\_level）

## Context（为什么做）

当前 hczkbot 的安全防护是**分散的二元开关**（`restrict_to_workspace`、`allow_patterns`/`deny_patterns`、`ssrf_whitelist` 等），没有统一的"防护等级"概念。用户要调整 Shell 拦截强度只能逐条改 `allow_patterns`/`deny_patterns`。

**真实摩擦**：Shell 的"下载执行阻断"（`curl … | sh`）会拦截 rustup、homebrew 等合法安装脚本，用户只能逐条加 `allow_patterns` 绕过。

**是否值得做**：值得。理由——(1) Shell deny-list 对合法工作流造成真实摩擦；(2) 范围有界：SSRF + 工作区边界始终开启，避免最灾难性后果（云元数据泄露、任意磁盘读写）；(3) 实现干净，与现有 `restrict_to_workspace` 注入模式一致；(4) power user / 单用户本地部署 / 安全研究有真实需求。

**目标**：新增 `guard_level` 配置字段（命名枚举），3 级：`standard`（默认全开）/ `minimal`（仅灾难 Shell 拦截）/ `off`（零注入+Shell 拦截，保留 SSRF+工作区边界）。

### 关于"最高级不做任何拦截"的范围界定

用户原话"最高级本应用不做任何拦截"结合已确认的拦截范围"注入+Shell拦截"，界定如下：

* **`off`** **级关闭（用户确认的范围内）**：所有注入防护（web 不可信横幅、system-prompt 不可信声明片段）+ 所有 Shell 硬编码 deny-list（含灾难命令 `rm -rf /`、下载执行阻断 `curl|sh`、内部状态文件保护）。即应用不再因提示词注入顾虑拦截任何 Shell 命令或标记任何外部内容。

* **`off`** **级保留（结构性边界，非"注入+Shell拦截"）**：SSRF 网络隔离、工作区路径边界、环境变量白名单、子 agent 隔离、runtime context 标签。这些是与提示词注入无关的结构性访问控制——关闭它们会导致云元数据泄露、任意磁盘读写等与注入灵活性无关的灾难性后果。

> ⚠️ **如果用户希望** **`off`** **也关闭 SSRF + 工作区边界**（真正的零拦截），请在审批时说明，我会调整矩阵让这两项也跟随 `guard_level`。当前设计倾向于保留它们作为结构性安全底线。

## 等级矩阵

| 机制                                                 | standard | minimal | off | 类别       |
| -------------------------------------------------- | :------: | :-----: | :-: | -------- |
| Shell 灾难命令（rm -rf /、mkfs、dd→设备、fork bomb、shutdown） |     ✅    |    ✅    |  ❌  | Shell 拦截 |
| Shell 下载执行阻断（curl\|sh、base64\|sh、eval curl）        |     ✅    |    ❌    |  ❌  | Shell 拦截 |
| Shell 内部状态文件保护（写 history.jsonl/.dream\_cursor）     |     ✅    |    ❌    |  ❌  | Shell 拦截 |
| web\_fetch 不可信横幅 `[External content — …]`          |     ✅    |    ❌    |  ❌  | 注入防护     |
| system-prompt 不可信声明片段（untrusted\_content.md）       |     ✅    |    ✅    |  ❌  | 注入防护     |
| SSRF 网络隔离                                          |     ✅    |    ✅    |  ✅  | 始终开启     |
| 工作区路径边界                                            |     ✅    |    ✅    |  ✅  | 始终开启     |
| 环境变量白名单（防 API key 泄漏给子进程）                          |     ✅    |    ✅    |  ✅  | 始终开启     |
| 子 agent 隔离（独立 registry、不加载 MCP）                    |     ✅    |    ✅    |  ✅  | 始终开启     |
| runtime context 标签（元数据卫生，非内容防御）                    |     ✅    |    ✅    |  ✅  | 始终开启     |

> 用户配置的 `allow_patterns`/`deny_patterns` 在所有等级都生效（那是用户自己的规则，非应用默认拦截）。`off` 只关闭应用硬编码的 deny-list。

## 设计

### 新增 `hczkbot/security/guard_level.py`（新文件）

集中等级→特性映射，单一真相源，便于审计：

```python
from dataclasses import dataclass

STANDARD = "standard"
MINIMAL = "minimal"
OFF = "off"
_VALID = (STANDARD, MINIMAL, OFF)

@dataclass(frozen=True)
class GuardPolicy:
    level: str = STANDARD
    def __post_init__(self):
        if self.level not in _VALID:
            object.__setattr__(self, "level", STANDARD)
    @property
    def shell_denylist(self) -> bool:       # 完整 deny-list（含下载执行+状态文件）
        return self.level == STANDARD
    @property
    def catastrophic_shell_blocks(self) -> bool:  # 仅灾难命令
        return self.level in (STANDARD, MINIMAL)
    @property
    def untrusted_banner(self) -> bool:     # web_fetch 横幅
        return self.level == STANDARD
    @property
    def untrusted_snippet(self) -> bool:    # system-prompt 片段
        return self.level in (STANDARD, MINIMAL)
```

### 配置字段 — `hczkbot/config/schema.py` `ToolsConfig`（与 `restrict_to_workspace` 同级）

```python
guard_level: str = Field(
    default="standard",
    validation_alias=AliasChoices("guardLevel", "guard_level"),
)
```

加 `@field_validator("guard_level", mode="before")` 做小写化 + 非法值回落 `standard`。

### 注入路径（遵循现有 `restrict_to_workspace` 惯例）

`ToolsConfig.guard_level` → `ToolContext(config=self.tools_config)`（loop.py:517）→ 各工具 `create(ctx)` 读 `ctx.config.guard_level` → 存实例属性 → `execute` 时用。

### 1. `hczkbot/security/guard_level.py`（新建）

* `config.example.json` 加 `"guardLevel": "standard"`（带注释说明三档）。

### 3. `hczkbot/agent/tools/shell.py`

* 把 `__init__` 里硬编码 deny 列表（当前 L179-205）拆成两个模块级常量：

  * `_CATASTROPHIC_DENY_PATTERNS`（L180-188：rm -rf、mkfs、dd if=、fork bomb、shutdown 等）

  * `_FRICTION_DENY_PATTERNS`（L189-204：下载执行阻断 + 内部状态文件保护）

* `__init__` 加 `guard_level` 形参，存 `self.guard_level`；按 `GuardPolicy(self.guard_level)` 构建 `self.deny_patterns`：

  * `shell_denylist` → 用户 deny + catastrophic + friction

  * `catastrophic_shell_blocks` → 用户 deny + catastrophic

  * 否则 → 用户 deny only

* `_guard_command`（L596-666）**不改**——deny\_patterns 已是 level-aware；SSRF（L621-629）和工作区越界（L631-664）检查始终运行。
